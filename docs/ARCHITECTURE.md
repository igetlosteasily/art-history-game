# Art History Study: Architecture

A map of where everything lives and why it lives there. Written for Chase as much as for Claude Code: if you understand this page, you understand the shape of the whole app.

## The big idea: separate things that change for different reasons

The original game was one file that held the data, the rules, the layout, and the styling all mixed together. That works for a prototype, but it means changing a color, a painting, or a rule all happen in the same place, and any change risks breaking something unrelated.

The rebuild separates the app into layers, each answering one question:

| Layer | Folder | The question it answers | Who usually changes it |
| --- | --- | --- | --- |
| Data | `src/data/` | What paintings and movements exist? | Chase, often |
| Logic | `src/lib/` | What are the rules? (dealing rounds, grading, scoring) | Rarely, carefully, with tests |
| Components | `src/components/` | What are the reusable pieces of the interface? | When the design changes |
| Screens | `src/screens/` | How are the pieces arranged for each mode? | When a mode's flow changes |
| Styles | `src/styles/` and each component's `.css` | What does it look like? | When the design changes |

A useful way to think about it: **data is the collection, logic is the museum's rules, components are the furniture, screens are the rooms, styles are the lighting and paint.**

## Why these choices

**Keep React and Vite.** They are already in the repo, they are the most common pairing for small web apps today, and switching would teach Chase a new tool instead of building on the one he has. *Words to know:* **React** lets us build the interface from components (reusable pieces) whose appearance follows from their data. **Vite** runs a fast local preview while we work and packages the app for the web.

**Each component gets a folder with its own `.jsx` and `.css`.** Everything about one piece of the interface lives together, so "where is the wall label?" has one answer. The original put all styling inline in JavaScript; moving it to CSS files separates *what it is* from *how it looks*, and lets the design tokens work.

**Plain CSS with custom properties (tokens), not a styling framework.** Frameworks like Tailwind are popular but put dozens of short class names on every element, which is hard for a beginner to read. Plain CSS reads like the design document: `color: var(--bronze)` says exactly what it means, and changing a token in `tokens.css` changes it everywhere.

**Logic lives in `src/lib/` as pure functions with tests.** A pure function takes inputs and returns outputs without touching the screen. That makes rules like grading easy to test automatically: we write down examples ("Gericalt" should count as Géricault) and the computer checks them every time anything changes. *Word to know:* a **test** is a small program that checks another program's behavior.

**A tiny hash router instead of a routing library.** The part of a URL after `#` (like `#/identify`) can say which screen to show. With only a few screens, a 15-line hook is easier to understand than a library and needs no special server settings.

**Data in plain JavaScript files.** Chase can add a painting by copying an entry and editing it. No database is needed for Study.

**Images processed by a script, not by hand.** The script makes small, fast copies at two sizes and records their dimensions. Chase keeps adding originals; one command regenerates the web versions.

**Leaderboard behind a serverless function (arcade only).** The browser can never be trusted with a database password, because anyone can read code that runs in their browser. A serverless function is a small piece of code that runs on Vercel's servers when called. It holds the secret, checks every score, and talks to the database on the browser's behalf.

## How a change flows (the modern, AI-partnered workflow)

1. Describe the change to Claude Code in plain language.
2. Claude Code makes a plan, then edits files on a **branch** (a separate line of work that does not disturb the main version).
3. Tests, lint, and build run to catch mistakes.
4. The branch is **pushed** to GitHub, and Vercel automatically builds a **preview URL**: a live, private-ish copy of the app with that change.
5. Review the preview on a phone and a laptop.
6. If it is good, the branch is **merged** through a **pull request** (a proposal to combine changes, with a description and a place for comments).

Understanding this loop matters more than memorizing syntax: it is how almost all software is made today, with or without AI.
